# Agent Workbench
## Two-page approval brief | 25 September 2026 | Proposed, not yet built

### Page 1 - Product and customer journeys

**What I will build.** A local-first workbench for technical product builders and developers to create, understand, test and improve agentic applications. Five top-level modes share one project, application graph, credential registry and run history. The current HTML is a design prototype; phase 1 replaces its fixtures with real execution. The graph is the operating interface, with explicit data, permissions, checks and failure routes.

**Readable by design.** Use ChatGPT/Codex-inspired neutral colors, sans-serif typography and restrained panels, with Light / Dark / System themes. Use 14px node labels and 12px edge labels at default zoom; pan instead of shrinking the whole app to fit. The left panel holds the selected mode's sub-tabs; the center holds its primary work; the right inspector shows contextual detail. UI, DB/auth wiring and Markdown remain in searchable, collapsed **Hidden nodes**. Their failures still surface in traces.

**One onboarding flow, two credential scopes.** Create/select a project, then build or connect an app. Planning and review agents need a workbench model credential; the target app may have separate runtime credentials and authentication. Add and validate each only when needed.

**1. Build - Align / Review / Run & Test / Launch.** Describe the app; the alignment agent clarifies its users, inputs, outputs, tools, prohibited actions and success criteria, then proposes a structure for approval. Review the generated graph and edit prompts, schemas, code references and connection rules. Before running, validate credentials, a compatible model, required data/tool connections and budgets. Observe real execution and inspect each invocation; turn failures into test cases. Launch initially downloads a runnable project ZIP: source, graph, prompts, dependencies, tests, README and a secret-free environment template. A clean install and sample run must pass before export is called ready.

**2. Connect & Debug - Connect / Map / Observe / Diagnose.** Select a GitHub repo or local checkout, pin its revision, and detect entry points, model calls, tools and supporting files. Review the inferred map and unresolved sections. Connect a running local app through an adapter, verify a test trace, then inspect node inputs, outputs, errors and timing. Diagnosis links an event to its source and can propose a reviewable patch. Source discovery works before instrumentation; live observability does not. Unsupported behavior stays visible as an opaque component, never an invented execution edge.

**3. Red Team - Scope / Test Plan / Run / Findings.** Connect an owned local/staging target and define its brand rules, intended behavior, allowed probes and call budget. A master agent proposes a bounded specialist team for security, prompt injection, brand behavior and customer experience. Review the plan before source review and behavioral probes execute. Findings include affected node/source, severity, evidence and reproduction steps; distinguish reproduced failures from code-only suspicions and inconclusive tests. Retest a fix and promote the case to an eval. Use isolated test identities/storage and disabled billing; exclude production probing, destructive actions and real-secret extraction.

**4. Model Lab - Configure / Compare / Graph Results.** Choose an app revision and the model node(s) to replace. Add up to five candidate model/provider configurations, each with a validated credential; models from one provider may reuse a key. Run one prompt with pinned retrieval, tool policy and isolated state. Offer fixed-input node comparison separately from full-workflow comparison, where downstream paths may diverge. Compare final answers, errors, latency, usage, available cost estimates and per-node outputs. Fixed model calls remain pinned and disclosed. Unsupported overrides are disabled with a reason; one failed provider does not discard the other results. Keep provider fallback off. One prompt is an exploratory comparison, not a reliable model ranking.

**5. Evals - Dataset / Criteria / Run / Results.** Import cases or derive candidates from the brief, traces and red-team findings. Review expected outcomes, deterministic checks and any model-judge rubric before saving a versioned suite. Run against a pinned app/model configuration; inspect per-case and per-node results, judge explanations, errors and regressions against a baseline. Failed infrastructure is an error, not an automatic quality failure; absent ground truth is marked unscored. Convert confirmed failures into repeatable regression cases.

### Page 2 - Scope, architecture and acceptance

**Model compatibility.** Phase 1 targets Gemini, OpenAI, Anthropic, Groq and OpenRouter adapters; discovery uses provider metadata plus our tested capability registry. Show runnable choices only after checking account access, tools, structured output, modality, context limits and the app adapter's override support. A valid key alone does not prove compatibility. Metadata checks precede any disclosed, capped inference probe.

**Credential and failure behavior.** After approval, load your Gemini credential from the specified MySecrets files server-side; inspect only the relevant entries. Keys never enter browser storage, prompts, source exports or traces. Missing/invalid keys, inaccessible repos, absent datasets and missing instrumentation offer a precise next step. Rate limits, timeouts, tool failures, exhausted budgets and cancellation retain partial evidence. Persist redacted run events locally; interrupted runs are marked interrupted after restart, without silently replaying side effects. Revisions remain immutable while a new draft is edited.

**Proposed architecture.** React/TypeScript UI and a Node/TypeScript local service, with a shared versioned graph/run contract. One scheduler enforces schemas, tool permissions, timeouts, bounded retries and shared call/cost/concurrency limits across every mode; agents plan, generate and review inside those limits. New apps use our manifest runtime. Imported apps stay code-owned and connect through an adapter; patches require review. Docker workers restrict filesystem, network and credentials; execution preflight checks Docker availability. Provider adapters normalize calls without hiding unsupported features. An append-only local event/artifact store drives all five modes. Hosted database, account auth and deployment remain phase 3; phase 1 still needs local persistence and security boundaries.

**First integration: Agentic Learning Studio.** Read-only inspection verified `APareek89/agentic-learning-studio`, main revision `5968d23`. Its current `/api/overview` and `/api/build` use `src/agent/orchestrator.ts`; `src/agent/graph.ts` serves a legacy path. Start with its actual TypeScript workflow and trace hooks, not a LangGraph-only importer. The model factory is Anthropic-specific: Gemini requires per-run provider injection in an isolated test copy, not just a new API key. Repo access is verified; live compatibility is untested.

**Phase 1 delivery boundary.** All five modes must complete a real, bounded journey: create/export one agent app; import and trace Learning Studio; reproduce a controlled red-team finding; compare compatible model configurations; and run a reviewed eval suite. Support one proven application adapter first, with explicit coverage for everything else. Validate five-slot behavior with controlled fixtures, and live integrations only with valid credentials; untested providers cannot be labelled verified. Phase 2 improves our agent planning, coordination and resilience. Phase 3 adds hosted DB/auth, multi-user operation and launching apps from the site.

**Customer-journey QA is a release gate.** Before handoff, demonstrate and retain evidence for: (1) prompt-to-export and clean-machine run; (2) missing/invalid keys and incompatible models; (3) public/private/missing repos and unrecognized code; (4) graph without traces, then verified instrumentation; (5) node edits, schema mismatch and bounded reflection; (6) red-team scope limits, evidence and retest; (7) five comparison slots with a timeout, invalid key and pinned model; (8) eval import, rubric changes and regression detection; (9) stop, disconnect, restart and partial recovery; (10) secret redaction, permissions and candidate-state isolation; (11) light/dark readability, keyboard navigation and responsive panels. Handoff includes pass/fail evidence and clearly labelled gaps, not a polished happy-path demonstration.

**Power Coding and approval.** Use this brief as product context for Handoff, Learning, journey-based Loop evals, architecture diagrams, checkpoints and failure-mode reviews after approval. Run free checks before paid integration tests; set a bounded live-test budget. This turn produces the brief only: no application implementation or paid calls. Your go-ahead approves this architecture and bounded phase-1 scope; operational skill preferences are configured at setup.
